# 上下文与提示缓存：一次对话到底发了多少东西

> 语言：中文（摸索阶段只维护中文版）
> 所属：[技术原理](README.md) · 更新：2026-09-16 · 前置阅读：[04 拆解 Agent 接入](04-agent-tool-loop.md)

[《拆解 Agent 接入》](04-agent-tool-loop.md)里有一句话，当时一带而过：**Messages API 是无状态的，模型每次只能看到这一次请求里的内容。**

这句话有一个直接后果：对话进行到第十轮时，我们仍然要把前面九轮的全部内容重新发一遍。再加上 StyleAI 的工具定义、系统提示词、技巧卡索引，每一次请求都不小。而一轮对话里，模型往往要调用好几次。

那么，一次对话到底发送了多少内容？这些内容怎样影响成本和延迟？提示缓存是怎样避免重复付费的，什么情况下它会突然失效？

本文按“一次请求里有什么 → 重复发送的代价 → 缓存怎么工作 → 什么会让缓存失效 → StyleAI 怎样排布上下文”的顺序展开。文中的 token 数是按 StyleAI 的设计估算的，用来说明数量级和增长方式；真实数值要在 M0 用 token 计数接口实测。

## 一次请求里有什么

一次 Messages API 请求的内容分成三块，按照发送时的顺序：

```text
┌─ tools ─────────────────────────────────────────────┐
│ 12 个工具的名称、描述、JSON Schema                    │  每次请求完全相同
├─ system ────────────────────────────────────────────┤
│ 人格与造型原则、输出要求、技巧卡索引                    │  每次请求完全相同
├─ messages ──────────────────────────────────────────┤
│ 用户消息、模型回复、工具调用、工具结果……（按时间排列）    │  每轮追加
└─────────────────────────────────────────────────────┘
```

StyleAI 各部分的估算：

| 部分 | 内容 | 估算 token | 变化频率 |
| --- | --- | --- | --- |
| 工具定义 | 12 个工具，平均每个约 150 token | ~1,800 | 随版本发布 |
| 系统提示词 | 人格、造型原则、输出要求、安全约束 | ~3,000 | 随版本发布 |
| 技巧卡索引 | 约 150 张卡的编号、标题、标签 | ~4,200 | 知识库更新 |
| 用户记忆与衣橱概况 | 偏好、禁忌、件数与类目分布 | ~400 | 每轮可能变化 |
| 每轮用户消息 | 一句话到一段话 | ~120 | 每轮追加 |
| 每轮模型回复 | 文字 + 工具调用 | ~400 | 每轮追加 |
| 每轮工具结果 | 衣橱检索、技巧卡正文、品牌商品 | ~1,500 | 每轮追加 |

前三项加起来约 9,000 token，占了不小的比重，而且**每次请求一模一样**。

## 重复发送的代价

一轮对话中，模型通常要调用三次：第一次决定查什么，第二次拿到工具结果后继续，第三次给出方案。每次调用都要重新发送全部上下文。

按上面的估算，如果一轮对话追加约 2,000 token（用户消息 + 回复 + 工具结果），十轮对话的输入量是这样增长的（价格按 Claude Opus 5 的公开定价，输入 $5 / 百万 token，输出 $25 / 百万 token）：

```text
turn  history  input/req  in tokens  no cache $  cached $
   1     2020       9620      28860      0.1693    0.0478
   2     4040      11640      34920      0.1996    0.0508
   3     6060      13660      40980      0.2299    0.0539
   4     8080      15680      47040      0.2602    0.0569
   5    10100      17700      53100      0.2905    0.0599
   6    12120      19720      59160      0.3208    0.0630
   7    14140      21740      65220      0.3511    0.0660
   8    16160      23760      71280      0.3814    0.0690
   9    18180      25780      77340      0.4117    0.0720
  10    20200      27800      83400      0.4420    0.0751
total                                     3.0565    0.6144
saving: 80%
```

几个可以直接读出来的事实：

- **单次请求的输入量随轮数线性增长**：第 1 轮约 9,600 token，第 10 轮约 27,800。
- **一轮对话要发送的总量是它的三倍**，因为要调用三次模型。
- **十轮对话的输入总量约 56 万 token**，而用户真正输入的文字只有 1,200 token 左右。

“cached”一列的假设是：重复的部分按输入价格的 10% 计费。实际倍率以官方定价为准，但趋势是确定的——**在这种结构下，节省的比例很高，因为绝大部分内容每次都一样。**

（表中的数字由实验脚本按上述假设计算，不是实测值，仅用于说明增长方式。）

## 提示缓存怎么工作

提示缓存的规则可以用一句话概括：**它缓存的是请求内容的前缀。**

一次请求的内容按固定顺序拼接：`tools` → `system` → `messages`。服务端会找出这次请求和缓存内容**从开头开始最长的相同部分**，这部分直接复用，不再重新计算；从第一处不同开始，后面的全部重新计算。

```text
第 1 次请求   [工具定义][系统提示][技巧卡索引][第 1 轮消息]
                                             ↑ 写入缓存

第 2 次请求   [工具定义][系统提示][技巧卡索引][第 1 轮消息][第 2 轮消息]
              └────────── 完全相同，命中缓存 ──────────┘└─ 新内容 ─┘
```

使用时的几个要点：

| 事项 | 说明 |
| --- | --- |
| 缓存断点 | 在内容块上标记 `cache_control`，表示“到这里为止的内容请缓存”。一次请求最多 4 个断点 |
| 有效期 | 默认 5 分钟，也可以选择 1 小时；每次命中会续期 |
| 最短长度 | 太短的前缀不会被缓存，下限与模型有关（数百到数千 token 量级） |
| 写入成本 | 第一次写入缓存的价格高于普通输入 token，命中读取则便宜得多。所以只有会被重复使用的前缀值得缓存 |
| 命中情况 | 响应的 `usage` 中有 `cache_creation_input_tokens`（写入）与 `cache_read_input_tokens`（命中），可以直接观察 |

对 StyleAI 来说，断点放在“技巧卡索引之后、对话历史之前”，正好把前面估算的约 9,000 token 稳定内容全部包住。

## 什么会让缓存失效

因为匹配的是前缀，**越靠前的内容变化，影响越大**。

| 做法 | 后果 |
| --- | --- |
| 增删或修改一个工具 | `tools` 在最前面，整份缓存作废 |
| 系统提示词里写当前时间、用户昵称、随机请求 ID | 每次请求都不同，`system` 之后全部作废 |
| 技巧卡索引每次序列化顺序不同 | 同上；JSON 序列化要固定键顺序 |
| 会话中途更改模型或 effort | 缓存按模型与参数区分，历史部分需要重新写入 |
| 修改或删除历史中较早的消息 | 从修改处往后全部作废 |
| 超过有效期没有新请求 | 缓存过期，下次重新写入 |

StyleAI 对应的做法：

- 工具定义与系统提示词随版本发布，运行期间不随请求变化；
- 技巧卡索引按编号排序后序列化；
- 用户记忆、衣橱概况这类每轮可能变化的内容，**不放进 `system`**，而是作为对话历史最前面的一条消息；
- 一轮对话内不改 effort；确实需要更高 effort 时，在新一轮开始时切换。

## 长对话怎么办

缓存解决的是“重复内容不重复付费”，但解决不了“内容一直变多”。对话足够长时，上下文窗口会被塞满，每轮新增的部分也在持续增加。

三种手段：

| 手段 | 做法 | 代价 |
| --- | --- | --- |
| 服务端压缩 | API 在接近阈值时自动把较早的历史总结成摘要 | 细节丢失；压缩块必须原样回传 |
| 上下文编辑 | 清除较早的工具结果或思考块 | 修改了历史，缓存从修改处往后失效 |
| 应用侧重查 | 旧的工具结果直接丢弃，模型需要时重新调用工具 | 多一次工具调用 |

StyleAI 的策略建立在一个事实上：**事实性信息的真值在数据库里，不在对话历史里。** 衣橱、方案、品牌商品都可以随时用工具重新查询，所以较早的工具结果并不需要一直留在上下文中。

具体做法：保留最近若干轮的完整工具结果，更早的替换为一句占位说明（“该结果已省略，可重新调用工具获取”）。因为修改历史会让缓存从修改处失效，这个替换只在跨过阈值时做一次，而不是每轮都做。

## 工具结果是上下文里最容易失控的部分

前面估算每轮工具结果约 1,500 token，这个数字完全取决于工具怎么写。

| 写法 | 结果 |
| --- | --- |
| 返回抓取到的整页 HTML | 一次几万 token，几轮就把上下文占满 |
| 返回 50 件衣服的全部字段 | 大部分字段模型用不到 |
| 返回图片的 base64 内容 | 图片按尺寸折算 token，代价远高于文字 |
| 返回编号 + 少量关键字段，并说明“还有 N 条，可以继续检索” | 每次几百 token，模型需要细节时再查 |

《开发规范》因此规定单个工具结果不超过约 4K token，并要求列表结果设上限、说明是否被截断。

图片同理：对话过程中传给模型的是衣服的标签和颜色数值，不是图片本身；只有打标和效果图检查这两个必须看图的环节才传图片。

## 怎么验证缓存真的生效

每次模型调用都把 `usage` 的四个字段写入 Agent trace：

| 字段 | 含义 |
| --- | --- |
| `input_tokens` | 本次新计算的输入 token |
| `cache_creation_input_tokens` | 写入缓存的 token |
| `cache_read_input_tokens` | 命中缓存的 token |
| `output_tokens` | 输出 token |

判断标准很简单：**同一会话的第二次及以后的调用，`cache_read_input_tokens` 应该稳定地接近前缀大小。** 如果一直是 0，说明前缀里混进了每次都变化的内容，需要按上一节的清单排查。

M0 还会用 token 计数接口核对本文的估算值，把真实的前缀大小、每轮增量写回文档。

## 小结

Messages API 无状态，所以每次请求都要重发全部上下文；一轮对话要调用几次模型，重发的量随轮数线性增长。提示缓存按前缀匹配复用这部分内容，代价是前缀必须逐字节稳定：工具定义、系统提示词、索引这些内容要固定下来，变化的内容往后放。

上下文里增长最快的不是用户说的话，而是工具结果。控制住工具结果的大小，比任何缓存技巧都有效。

读完本文，可以试着回答：如果我们决定让 Agent 在系统提示词里知道“今天是几月几号”，会发生什么？有没有既让模型知道日期、又不破坏缓存的做法？
