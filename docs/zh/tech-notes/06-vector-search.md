# 相似单品怎么找：向量、余弦相似度与近似检索

> 语言：**中文** · 日本語（翻译中） · English（翻译中）
> 所属：[技术原理](README.md) · 更新：2026-09-16 · 实验代码：[labs/vector-search](../../tech-notes/labs/vector-search/)

StyleAI 里有几个问题，用 SQL 不太好写：

- 用户说“再给我看几件和这件类似的上衣”；
- Agent 想找“适合这套街头风方案的外套”；
- 学习管线拿到一张候选技巧卡，要判断知识库里是不是已经有意思相同的卡片；
- 用户看中一件贵的外套，想找“衣橱里有没有能替代的”。

这些问题都在问“像不像”。而 `WHERE category = 'outerwear' AND color = 'navy'` 只能回答“是不是”。

本文从“把一件衣服变成一串数字”开始，说明相似度是怎么算的、为什么大规模检索要用近似算法、过滤条件和向量检索的先后顺序会造成什么差别，最后回到 pgvector，看这些机制在数据库里怎么落地。

实验用程序生成的两万个玩具向量代替真实的模型输出，因为本文关心的是检索机制本身，而不是某个向量模型的效果。实验代码见 [vector_lab.py](../../tech-notes/labs/vector-search/vector_lab.py)，下文输出来自实际运行。

## 属性过滤解决不了的问题

衣橱里的每件衣服都有结构化标签：类目、颜色、材质、廓形、正式度、风格标签。按这些字段过滤很直接：

```sql
SELECT * FROM garments
WHERE user_id = $1 AND category = 'bottoms' AND formality <= 2;
```

但“和这件灰卫衣气质相近的上衣”没法这样写。可以尝试用标签组合近似：同为街头风、同为宽松廓形、颜色接近……很快就会遇到两个麻烦：

1. **权重难定。** 风格标签一致但颜色差很多，和颜色接近但风格不同，哪个更“像”？写成 SQL 就要给每个条件一个权重，而这些权重没有依据。
2. **标签是离散的。** “街头”和“运动”是两个标签，但它们之间的距离，比“街头”和“正装”近得多。等值比较表达不出这种远近。

**相似不是一个是非问题，而是程度问题。** 要按程度排序，就需要一个能计算距离的表示方法。

## 把衣服变成向量

向量模型（embedding model）做的事情是：把一张图片或一段文字，映射成一串固定长度的数字，并且让**内容相近的输入，得到的向量在空间中也相近**。

```text
真值图（灰卫衣） ──向量模型──► [0.021, -0.115, 0.084, ... ]   共 N 个数
标签文本                        [0.019, -0.108, 0.091, ... ]   同一个空间
```

几个要点：

- **维度固定。** 同一个模型输出的向量长度相同，比如 1024 维。维度由模型决定，不能自己截断（除非模型明确支持）。
- **单个数字没有含义。** 第 37 维不代表“袖长”。有含义的是向量之间的**相对位置**。
- **多模态模型让图片和文字落在同一个空间。** StyleAI 计划使用的 `voyage-multimodal-3.5` 就是这类模型：图片和文字经过同一个编码器，因此可以用一段文字去检索图片。
- **向量通常归一化成单位长度**（模长为 1），这会让后面的相似度计算更简单。

StyleAI 为每件衣服保存两条向量：

| 向量 | 输入 | 用途 |
| --- | --- | --- |
| `image_embedding` | 真值图（抠图后的衣服） | “看起来像”的检索：版型、图案、质感 |
| `text_embedding` | 标签拼成的描述文本 | “说起来像”的检索：Agent 用自然语言描述想要的单品 |

两条向量分开保存，是因为它们回答不同的问题。一条印花复杂的 T 恤和一条印花简单的 T 恤，图片向量差别大，文本向量可能几乎一样。

技巧卡也保存向量，输入是卡片正文，用于按场景检索和去重。

## 相似度怎么算

最常用的两种度量：

```text
余弦相似度   cos(a, b) = (a · b) / (|a| × |b|)      取值 -1 ~ 1，越大越像
欧氏距离     L2(a, b)  = √Σ(aᵢ - bᵢ)²               越小越像
```

对**单位长度**的向量，两者是等价的：

```text
L2² = |a|² + |b|² - 2(a · b) = 2 - 2·cos(a, b)
```

实验 [1] 用一个查询验证这一点：

```text
[1] cosine similarity vs Euclidean distance (unit vectors)
  same top-10 set: True
  relation check: max |L2^2 - (2 - 2*cos)| = 1.33e-15
```

两种度量给出的前 10 名完全相同，等式在浮点误差范围内成立（最大偏差约 1.3×10⁻¹⁵，就是双精度浮点的舍入误差）。

**所以，只要向量都归一化，用余弦还是欧氏距离不影响排序结果。** 真正需要注意的是：数据库索引在创建时要指定距离函数，查询时必须使用同一种，否则索引不会被使用，或者结果不对。

## 精确检索要花多少时间

最直接的检索方式是把查询向量和每一个候选向量都算一遍相似度，再取前 k 个。计算量是 O(N × d)：N 个向量，每个 d 维。

实验 [2] 在两万个 64 维向量上测量：

```text
[2] exact search: 0.5 ms per query, scans 20000 vectors
```

0.5 毫秒，完全可以接受。但这个数字会随着两个方向变大：向量更多（真实的品牌目录可能有十万条），维度更高（常见的向量模型是 1024 维，是实验的 16 倍）。两项相乘，同样的实现会慢两个数量级。

StyleAI 的三类向量数据规模差别很大：

| 数据 | 规模 | 检索方式 |
| --- | --- | --- |
| 单个用户的衣橱 | 几十到几百件 | 先按 `user_id` 过滤，再精确检索即可 |
| 技巧卡 | 几百张 | 精确检索 |
| 品牌目录 | 可能十万级 | 需要索引 |

**先判断数据规模，再决定要不要近似检索。** 用户衣橱这种量级，加索引反而增加复杂度。

## 近似检索：只扫一部分

品牌目录这种规模，常用的办法是牺牲一点准确性换速度，称为近似最近邻检索。实验实现了其中最容易理解的一种思路，和 pgvector 的 IVFFlat 索引同源：

```text
建索引：把所有向量聚成若干个簇，记下每个簇的中心和成员
检索时：先算查询向量和各个簇中心的相似度
        只在最近的 n 个簇里做精确检索（n 称为 probes）
```

实验 [3] 把两万个向量分成 64 个簇，改变 probes 的值：

```text
[3] IVF-style index: 64 clusters, average 312 vectors per cluster
  probes  recall@10  scanned  ms/query
       1     16.80%      307       0.1
       2     26.40%      609       0.1
       4     39.00%     1199       0.2
       8     57.40%     2489       0.4
      16     75.40%     5006       0.8
      32     93.20%    10112       1.6
```

`recall@10` 是召回率：近似检索返回的前 10 个中，有多少确实属于精确检索的前 10 个。

结果很直观：**probes 越多，扫描的向量越多，速度越慢，召回率越高。** probes 等于簇的总数时，就退化成精确检索。

要注意，具体的召回率数值取决于数据分布和簇的数量，实验里的玩具数据偏分散，所以单个簇的召回率不高。真正要记住的是这条曲线的形状：**召回率的提升是有代价的，而且代价是可以调的**。上线时要先确定业务能接受的召回率，再反推参数。

pgvector 还提供另一种索引 HNSW，原理不同但取舍相同：它把向量组织成一张多层的邻居图，查询时从上层入口点出发，每次跳到更接近查询的邻居，逐层向下细化。查询参数 `ef_search` 控制搜索时保持的候选数量，作用类似这里的 probes：调大更准更慢。

## 过滤条件放在哪一步

实际查询几乎都带条件：只要外套、只要在售、只要这个用户的衣服。条件和向量检索的先后顺序，会得到不同的结果。

实验 [4] 在两万件中筛选 3,925 件外套：

```text
[4] filtering by category 'outerwear' (3925 of 20000 garments)
  filter after search: on average 2.2 of 10 results survive the filter
  filter before search: always 10 results, scans only matching vectors
```

- **先检索后过滤**：拿到最相似的 10 个，再扔掉不是外套的，平均只剩 2.2 个。想凑够 10 个外套，就要取更多候选再过滤，取多少没有定数。
- **先过滤后检索**：在 3,925 件外套里做精确检索，一定能得到 10 个结果。

在数据库里，这个选择还牵涉到索引：先过滤会让向量索引难以发挥作用（索引是按全表建的），条件选择性很高时，直接扫描过滤后的数据反而更快。pgvector 也提供了在有过滤条件时继续使用索引、必要时扩大扫描范围的机制，具体效果在 M1 用真实数据量测量。

StyleAI 的实际情况：衣橱检索的 `user_id` 条件选择性极高（几百件），直接精确检索；品牌目录的类目、在售状态条件选择性一般，需要实测两种顺序的差别。

## 在 pgvector 里怎么落地

```sql
-- One column per embedding; the dimension is fixed by the model.
ALTER TABLE brand_items ADD COLUMN embedding vector(1024);

-- Index and query must use the same distance function. <=> is cosine distance.
CREATE INDEX brand_items_embedding_idx ON brand_items
    USING hnsw (embedding vector_cosine_ops);

-- Nearest neighbours of a query vector.
SELECT id, title, 1 - (embedding <=> $1) AS similarity
FROM brand_items
WHERE availability = 'in_stock'
ORDER BY embedding <=> $1
LIMIT 10;
```

几个工程上的注意点：

| 事项 | 说明 |
| --- | --- |
| 距离函数一致 | 索引用 `vector_cosine_ops`，查询就要用 `<=>`；用成 `<->`（L2）索引不会生效 |
| 归一化 | 向量入库前统一归一化，余弦与 L2 的排序才一致 |
| 存储 | 1024 维 float32 每条 4 KB；十万条约 400 MB，再加索引。可以评估 pgvector 的半精度向量类型降低一半存储 |
| 版本字段 | 记录向量模型与版本；换模型后必须重新计算全部向量，不能新旧混用 |
| 重建 | 批量重算向量时，新列旁路写入、切换后再删除旧列，避免检索中断 |

## StyleAI 的用法

| 场景 | 用哪条向量 | 规模 | 方式 |
| --- | --- | --- | --- |
| “找几件类似的上衣” | 衣橱图片向量 | 几百 | 先按用户与类目过滤，精确检索 |
| Agent 用自然语言找单品 | 衣橱文本向量 | 几百 | 同上 |
| 技巧卡检索 | 卡片向量 + 标签过滤 | 几百 | 精确检索 |
| 品牌目录检索、平价替代 | 商品图片与文本向量 | 十万级 | 索引 + 条件过滤，参数按召回率要求确定 |
| 候选技巧卡去重 | 卡片向量 | 几百 | 精确检索，相似度超过阈值判为重复 |

去重阈值、召回率目标、索引参数都在 M1 用真实数据确定，并写回《技术选型》。

## 小结

把衣服变成向量，是为了让“像不像”变成可以计算、可以排序的量。向量归一化之后，余弦和欧氏距离等价；数据量小的时候精确检索就够用；数据量大的时候，用近似索引换速度，代价是召回率，而召回率可以通过参数调节。过滤条件和向量检索的先后顺序，同样要根据条件的选择性来定。

读完本文，可以试着回答：用户上传了一件新外套，我们想在品牌目录里找“风格接近但更便宜”的商品。应该用图片向量还是文本向量？价格条件应该放在检索之前还是之后？
