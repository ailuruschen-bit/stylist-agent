# 结构化输出：怎样保证模型返回的一定是合法 JSON

> 语言：**中文** · 日本語（翻译中） · English（翻译中）
> 所属：[技术原理](README.md) · 更新：2026-09-16 · 实验代码：[labs/constrained-output](../../tech-notes/labs/constrained-output/)

StyleAI 有四个地方需要模型返回**机器能直接用**的结果：

| 场景 | 需要的结构 |
| --- | --- |
| 衣橱打标 | 类目、颜色名、材质、廓形、正式度、玩法潜力 |
| 方案卡片 | 单品列表、层次角色、穿法、配色逻辑、引用的技巧卡 |
| 生图计划 | 阶段列表，每个阶段的参考图、要保真的细节、提示词 |
| 效果图检查 | 是否通过、问题列表（阶段、类型、描述） |

这些结果要写进数据库、驱动生图流水线。如果模型在 JSON 前面多写一句“好的，结果如下：”，或者把正式度写成 `"2"` 而不是 `2`，后面的代码就会失败。

常见的做法是在提示词里写“只返回 JSON，不要有其他内容”，再配上 `try/except` 和重试。这样能用，但不可靠：出错的概率不是零，而且每次重试都要重新付费和等待。

有没有办法让返回值**一定**符合我们定义的结构？有，而且原理不复杂。本文先看模型的输出是怎么产生的，再看约束解码做了什么，用一个玩具实验观察效果，最后回到 Claude 的两种用法和 StyleAI 的落地方式。

## 输出是怎么产生的

大模型生成文本的方式是自回归的：**一次生成一个 token，每一步都基于已经生成的内容**。

```text
已生成：{"category":
   │
   ▼
模型给出词表上每个 token 的分数（logits）
   │
   ├─ "tops"      2.9
   ├─ "hoodie"    1.7
   ├─ "outerwear" 1.2
   ├─ "grey"      0.4
   └─ ……（词表里其余几万个 token）
   │
   ▼
softmax 变成概率分布 → 采样 → 得到下一个 token
```

关键在于：**模型没有“输出一个合法 JSON”这个目标**，它只是一步步挑选概率高的 token。JSON 之所以通常是合法的，是因为训练数据里有大量 JSON，模型学到了“左括号之后通常跟键名”这种模式。合法性是副产品，不是保证。

## 提示词约束的极限

提示词能提高合法的概率，但改变不了机制。考虑一段有 200 个 token 的输出：即使每一步选错格式的概率只有 0.1%，整段输出全部正确的概率也只有约 82%（0.999²⁰⁰）。输出越长、结构越复杂，失败率越高。

实践中常见的失败形式：

| 失败形式 | 例子 |
| --- | --- |
| 前后多余的文字 | `好的，这是打标结果：{...}` |
| 包在代码块里 | ` ```json {...} ``` ` |
| 结构不完整 | 少一个右括号，或者最后一个字段被 `max_tokens` 截断 |
| 类型不对 | `"formality": "2"`（字符串）而不是 `2` |
| 枚举值自由发挥 | `"category": "sweatshirt"`，而我们只接受五个固定值 |
| 多出字段 | 模型热心地加了 `"note": "这件衣服很百搭"` |

这些都可以靠重试规避，代价是延迟和成本；而且重试也可能再次失败。

## 约束解码：把不合法的 token 直接屏蔽

更可靠的办法，是在**采样这一步**动手：每生成一个 token 之前，先算出“在当前位置，哪些 token 还有可能构成一个合法的结果”，把其余 token 的概率全部置零，再在剩下的里面按原有比例采样。

```text
模型给出的概率分布
   │
   ▼
根据 Schema 和已生成的内容，计算允许的 token 集合
   │
   ▼
把不允许的 token 概率置零，剩下的重新归一化
   │
   ▼
采样 → 下一个 token 一定不会破坏结构
```

这就是约束解码（constrained decoding）。它需要一个状态机：Schema 被编译成“在什么位置允许什么”的规则，生成过程沿着状态机推进。

两个重要的性质：

1. **它不改变模型的偏好**。在允许的 token 之间，相对概率保持不变，只是重新归一化。模型仍然在“说自己想说的”，只是不能说破坏结构的话。
2. **它只保证结构，不保证内容**。类目一定是五个枚举值之一，但可能选错了那一个。

## 实验：同一个生成器，加不加约束

实验把语言模型换成一个玩具生成器：22 个 token 的词表，9 个生成步骤，每步的分数由“正确答案附近的偏好 + 随机噪声”构成。目标是产出这样一个打标结果：

```json
{"category": "tops", "formality": 2}
```

需要先说明实验的边界：**这个玩具生成器比真实模型差得多**，所以下面的绝对数值没有参考价值。实验要展示的是机制，以及错误会跑到哪里去。

先看不加约束地采样 2000 次：

```text
[1] free sampling
  valid against the schema :   0.3%
  exactly the right values :   0.1%
  invalid example          : ```json"category":"hoodie","hoodie""category"2}
  invalid example          : {"grey":"tops"}"formality"524
  invalid example          : {"category":"accessories",:}{2
```

三个失败例子刚好覆盖了前面列举的几类问题：多出代码块标记、键名用了不该用的词、结构错乱。

同一个生成器，同一个随机种子，只是在每一步屏蔽掉不合法的 token：

```text
[2] constrained sampling (same generator, invalid tokens masked)
  valid against the schema : 100.0%
  exactly the right values :  51.7%
```

**合法率从 0.3% 变成 100%。** 这不是因为生成器变聪明了，而是因为不合法的输出根本无法被生成。

那么屏蔽对概率做了什么？实验 [3] 打印了“正式度数值”这一步的分布：

```text
[3] what masking does at one step (state 'value2': the formality number)
  token            free  constrained
  3              63.7%       78.3%
  2              16.4%       20.1%
  "shoes"         4.0%        0.0%  (blocked)
  :               2.4%        0.0%  (blocked)
  6               2.1%        0.0%  (blocked)
  "outerwear"     1.7%        0.0%  (blocked)
```

不允许的 token 被置零，剩下的按原比例放大：`3` 和 `2` 在屏蔽前的比值是 63.7 : 16.4，屏蔽后是 78.3 : 20.1，比值不变（约 3.9 : 1）。`6` 被挡住了，因为 Schema 规定正式度是 1 到 5 的整数。

**约束没有让生成器改变想法，只是拿走了那些会破坏结构的选项。** 这也解释了实验 [4]：

```text
[4] where the errors go
  free sampling      : 99.7% unusable output,  0.1% valid but wrong values
  constrained        :  0.0% unusable output, 48.3% valid but wrong values
```

结构错误从 99.7% 降到 0，但内容错误从 0.1% 升到 48.3%——原来那些“根本没法解析”的样本，现在变成了“能解析但值选错了”。这个玩具生成器本来就更喜欢 `3` 而不是正确答案 `2`，约束解码不会纠正这一点。

**结论很明确：结构由机制保证，内容仍然由模型的能力决定。**

## Claude 提供的两种机制

| 机制 | 约束的对象 | 怎么用 |
| --- | --- | --- |
| 结构化输出 `output_config.format` | 模型最终回答的内容 | 传入一份 JSON Schema，回答保证符合它 |
| 严格工具 `strict: true` | 工具调用的参数 | 在工具定义上开启，`input` 保证通过该工具的 Schema 校验 |

Python SDK 还提供 `client.messages.parse()`，直接传入 Pydantic 模型，返回已经校验过的对象。StyleAI 的接口模型本来就是 Pydantic，可以直接复用。

使用时需要知道的限制：

- Schema 中每个对象都必须写 `additionalProperties: false`；
- 不支持递归结构；
- 不支持数值范围（`minimum`、`maximum`）、字符串长度这类取值约束——这些要在业务层校验（Python、TypeScript SDK 会自动去掉这些关键字并在客户端校验）；
- 新 Schema 第一次使用时有一次编译开销，之后有缓存；
- 与引用（citations）功能不兼容；
- 模型因安全原因拒绝回答时，输出可能不符合 Schema，要检查 `stop_reason`；
- 输出被 `max_tokens` 截断时，同样可能得到不完整的 JSON，要留足输出预算。

## StyleAI 的用法

| 场景 | 机制 | Schema 要点 |
| --- | --- | --- |
| 衣橱打标 | `output_config.format` | 类目、材质、廓形全部用 `enum`；每个字段附带置信度 |
| 方案卡片 | `output_config.format` | 单品用编号引用，不允许模型自由写商品名 |
| 生图计划 | `output_config.format` | 阶段列表；`inputs` 只能引用已存在的编号（`model:*`、`garment:*`、`stage:*`） |
| 效果图检查 | `output_config.format` | `pass` 为布尔值；`issues` 的 `type` 用 `enum` |
| 所有自定义工具 | `strict: true` | 见《开发规范》第 9.3 节 |

### Schema 设计的几条经验

1. **能用枚举就不用自由文本。** 类目、层次角色、穿法、问题类型都是固定集合，写成 `enum`，既减少歧义，也让后续统计成为可能。
2. **结构尽量扁平。** 嵌套越深，模型越容易在中途走偏，编译出的状态机也越复杂。
3. **用编号引用，不用名字引用。** 方案里的单品写 `G-000127`，不写“灰色卫衣”，避免模型凭印象编造不存在的单品。
4. **可选字段越少越好。** 每个可选字段都是一个分支；确实可选的字段，给出明确的“无”值（例如空数组）比省略更容易处理。
5. **字段名对模型也是提示。** `must_keep` 比 `mk` 更能让模型理解该填什么。
6. **Schema 要版本化。** 存进数据库的结果记录 Schema 版本，升级后能知道哪些旧数据需要重算。

## 结构对了，内容还要检查

实验 [4] 说明的问题，在真实系统里同样存在。StyleAI 在 Schema 之外还有三层检查：

| 层 | 检查什么 | 例子 |
| --- | --- | --- |
| 取值范围 | Schema 表达不了的数值与长度约束 | 正式度必须在 1–5；颜色占比之和不超过 1 |
| 交叉一致性 | 字段之间是否自洽 | 正式度为 5 却带着“街头”风格标签，判为可疑，交给复核 |
| 业务事实 | 引用的对象是否真实存在 | 方案里的单品必须属于该用户；品牌商品必须在目录中且在售 |

其中最后一层最重要：**模型可以生成合法的编号格式，但生成不出数据库里没有的编号。** 这类检查只能由服务层做，不能交给 Schema 或提示词。

另外，打标结果的每个字段都带置信度，低于阈值的字段会交给更强的模型复核，仍不确定的在界面上标记为“待确认”。这是承认“内容正确性没有保证”之后的产品设计。

## 小结

模型逐个 token 生成内容，格式合法只是概率的结果。约束解码在采样这一步屏蔽掉会破坏结构的 token，把“大概率合法”变成“一定合法”，而且不改变模型在合法选项之间的偏好。

代价是要看清它保证了什么：**结构，不是内容**。实验中，结构错误清零的同时，内容错误从 0.1% 变成 48.3%——它们原本被掩盖在“解析失败”里。所以 Schema 之外，还需要取值检查、交叉一致性检查和业务事实校验。

读完本文，可以试着回答：生图计划里的 `inputs` 只能引用已存在的编号。这个约束能用 JSON Schema 表达吗？如果不能，应该在哪一层实现，失败时该怎样反馈给模型？
