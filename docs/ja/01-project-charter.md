## 1. ひとことで

**StyleAI v2 は、あなたとクローゼットを共有するスタイリストです。** 色と重ね着を理解し、アップロードされた服を一着ずつ読み取り、ブランド公式サイトでアイテムを探します。プロンプトも生成の段取りも自分で決め、ファッション誌を読んで新しいテクニックを学び続けます。

## 2. 背景

ハッカソンの demo（[HackathonPJT · deploy/lite-budget](https://github.com/ailuruschen-bit/HackathonPJT/tree/deploy/lite-budget)）は「服をアップロード → デジタルヒューマンが試着」の流れを検証し、同時にいくつかの問題も明らかにしました。

| demo での発見 | v2 への影響 |
| --- | --- |
| ユーザー本人のデジタルヒューマンには写真と体型パラメータが必要で、ハードルが高くプライバシーの負担も大きい | v2 は体型データを集めず、内蔵モデルに統一 |
| 試着の品質が大量の手書きプロンプトに依存し、ポーズや服が変わるたびに調整が必要 | v2 のプロンプトは Agent が提案内容から都度書く |
| 生成モデルによる切り抜きと試着は服のディテールを変えてしまい、プロンプトに「柄を勝手に作らないこと」と書かざるを得なかった | v2 は登録にセグメンテーションを使い、着用イメージは真値画像と比較して確認 |
| 「試着」は「着たらどう見えるか」にしか答えていない。「どう組み合わせるか」には答えていない | v2 の中心は試着からスタイリング提案へ |

## 3. ビジョンと位置づけ

v2 は重心を**試着**から**スタイリング**へ移します。どう着るか、なぜ素敵に見えるかを伝え、プロのモデルによる着用イメージでそれを示します。

ユーザーが信頼するスタイリストのような存在を目指します。専門知識があり、正直に話し、付き合ってくれて、しかもクローゼットの中身を全部知っている。

### プロダクトの原則

1. **まず手持ちの服から。** 提案の順序は「クローゼットのアイテム → クローゼット + 少しの新規アイテム → 完全に新しい組み合わせ」。買い物の提案は補助であって目的ではありません。
2. **すべての提案に理由がある。** なぜその配色が成立するのか、なぜそのレイヤー構成なのか、どのテクニックを使ったのかを説明します。
3. **体型を評価しない。体型を前提にしない。** 体型データを集めず、「細く見える」「気になる部分を隠す」といった表現も使わず、服同士の関係と着こなしだけを扱います。
4. **迎合よりも正直さ。** ユーザーが望む組み合わせが成立しないときは、理由を説明したうえで実現できる代案を出します。
5. **驚きには根拠を。** 変わった着こなし（腰巻き、片袖抜き、肩掛け）は、その服の実際の属性にもとづいて提案し、効果も説明します。

## 6. スコープ

**やること**

- ユーザーと何往復も対話し、シーン、気分、挑戦したいスタイルを理解する。画面と対話は中日英の三言語に対応
- アップロードされた服を切り抜き・分析・タグ付けして登録し、共有クローゼットをつくる。タグはユーザーが修正できる
- ブランド日本公式サイトの定番品と新作を探し、手持ちの服と組み合わせる
- アイテム、レイヤー構成、配色の考え方、着こなし、理由まで含む提案を出し、テクニックカードを引用する
- 内蔵モデルでプロ品質の着用イメージを生成し、複雑な提案は多段階で生成してセルフチェックする
- ユーザーが明示した好みや NG を記憶する。ユーザーは内容を確認・削除できる
- ファッション誌からテクニックを抽出し、評価と人の審査を経てナレッジベースに追加する

**やらないこと**

- ユーザーの体型データの収集や利用
- ユーザー本人の画像生成、写真ベースのデジタルヒューマン
- アプリ内での購入と決済（ブランド公式サイトへの遷移のみ）
- 注文履歴の取込と EC アカウント連携
- ネイティブのモバイルアプリ
- 事前に固定したプロンプトテンプレート
- ソーシャル機能（フォロー、コミュニティ共有、コメント）

## 7. コア機能

### 7.1 KNOW · スタイリング知識

**ユーザーにとっての価値**：提案の背後に体系的な専門知識があり、感覚ではなく理由を説明できる。

- 知識は「テクニックカード」として保存し、色（色相環の配色、明度と彩度の段階、ニュートラルカラーの比率）、レイヤード（インナー / ミドル / アウター / アクセントの 4 役割、丈・厚み・ゆとりの交互）、シルエットと比率（H / A / V / X ライン、上ゆる下タイト、ウエスト位置）、素材と柄（質感の対比、柄の大小、フォーマル度の統一）をカバーします。
- ナレッジ v1 は人手で約 150 枚のカードを整理し、上記 4 分類それぞれ 25 枚以上とします。
- すべての提案は最低 1 枚のカードを引用し、画面上で展開して確認できます。

**完了条件**：スタイリストが 30 件の提案を抜き取り検査し、引用カードと提案内容が一致している割合が 90% 以上。

### 7.2 CLOSET · クローゼット理解

**ユーザーにとっての価値**：写真を 1 枚上げれば、服が正確に記録される。手入力は不要。

- **入力**：平置きまたはハンガー掛けの写真。JPEG / PNG / HEIC、1 枚 15 MB まで。
- **処理**：切り抜き → 品質チェック → 色の抽出 → ビジョンでのタグ付け → ベクトル化。チェックに通らない場合は理由（全体が写っていない、複数の服が写っている、ぼやけているなど）を具体的に伝えます。
- **タグ項目**：カテゴリとサブカテゴリ、メインカラーとアクセントカラー（hex、比率、三言語の名称）、素材、柄、シルエット、着丈、フォーマル度（1–5）、季節、スタイルタグ、着こなしポテンシャル。
- **着こなしポテンシャル**：カテゴリと属性から可能な着こなしを判定します。例：袖のあるパーカーやシャツは腰巻き、前開きのトップスは片袖抜きや羽織り、カーディガンは肩掛け、ロング丈の T シャツはフロントイン。
- **修正**：ユーザーはどのタグも修正できます。修正された項目は自動更新で上書きされず、修正履歴は評価データになります。

**完了条件**：200 着のラベル付きセットで、カテゴリ・メインカラー・素材・シルエットの精度 90% 以上。アップロードから登録完了まで P50 20 秒以内。

### 7.3 SCOUT · ブランドアイテム探索

**ユーザーにとっての価値**：手持ちに合う「何を買えばいいか」がわかり、リンクは実際に購入できる。

- 第一弾 5 ブランドの日本公式サイトの商品を定期巡回し、定番品と今季の新作を区別してカタログに保存します。
- 対話中にカタログの結果が足りないときは、Agent がブランド公式ドメインに限定して検索し、見つけた商品をカタログに追加します。
- 提案で引用できるのはカタログに存在し在庫のある商品のみ。価格は日本円で表示し、公式リンクと取得日時を添えます。

**完了条件**：提案時点でリンクが開けて在庫がある割合 98% 以上。

### 7.4 COMPOSE · コーディネート提案

**ユーザーにとっての価値**：そのまま着られる、完成した提案が得られる。

- 対話から得たシーンと好み、ユーザーメモリ、クローゼット、ブランドカタログ、テクニックカードを組み合わせて提案を作ります。
- 生成後にまずルールで配色とレイヤーの整合性を確認し、それから保存と画像生成に進みます。
- 1 回の対話では基本的に安心できる提案を 1 つ。適切な場面では「意外だけど成立する」提案を添え、なぜ成立するのかを説明します。

提案カードの構成：

| 部分 | 内容 |
| --- | --- |
| タイトルとシーン | 例：「代官山の週末 · カジュアルだけどきちんと」 |
| アイテム一覧 | 各アイテムの画像、出所（クローゼット / ブランド）、レイヤーの役割、着こなし（例：「腰に巻く」） |
| 配色の説明 | 使った色とその関係。例：「杢グレーをベースに、ネイビーの胸ロゴとインディゴのデニムを響かせる」 |
| 理由 | なぜ良く見えるか、引用したテクニックカード |
| 代替アイテム | クローゼット内の代替、または購入できるブランド商品 |
| 着用イメージ | 生成中は段階ごとの進捗、完了後に最終画像 |

**完了条件**：スタイリストのブラインド評価で専門性の平均 4.0 / 5 以上。

### 7.5 RENDER · 自律的な画像生成

**ユーザーにとっての価値**：この提案をモデルが着たときの実際の見え方がわかる。

- プロンプトは Agent が提案から都度書きます。シンプルな提案は一回で生成し、複雑な提案（重ね着が多い、変わった着こなし）は複数段階に分けます。
- 各段階が終わるたびに提案カードに表示し、最終画像はチェックを受けます：アイテムが正しいか、色が再現されているか、着こなしが実現されているか、人体の構造が自然か。
- 出力規格：3:4、全身、スタジオのソフトライト、無地の明るい背景。
- 生成に失敗した場合はクレジットを消費せず、再試行できます。

**完了条件**：服の再現度で 4 / 5 以上の評価を受けた画像の割合 80% 以上。一段階生成の初回画像 P50 40 秒以内、多段階 P50 120 秒以内。

### 7.6 LEARN · 自己学習

**ユーザーにとっての価値**：提案が季節やトレンドに追いつき、内容が固定化しない。

- バックグラウンドで毎週、承認済みソースの新着記事を読み、候補カードを作ります。
- 候補カードは写しのチェック、重複排除、評価の回帰、人の審査を経て正式なナレッジに入ります。
- トレンド系のテクニックには有効期限があり、シーズンが過ぎると重みが自動的に下がります。

**完了条件**：新カード追加後も評価スコアが下がらない。ソース別の審査通過率を集計し、ソースの入れ替え判断に使う。

## 8. 対話の体験

### 8.1 Agent の話し方

| 要件 | 内容 |
| --- | --- |
| 言語 | ユーザーの言語に合わせる（中国語・日本語・英語）。日本語は親しみのある です・ます体 |
| トーン | 親しみやすく、専門的で、率直。よく知っているスタイリストの友人のように。感嘆符や絵文字は多用しない |
| 質問 | 情報が足りないときはまず質問し、一度に聞くのは最も重要な 1 つだけ |
| 説明 | 専門用語は初出時に一文で説明する |
| 境界 | 体型を評価しない。ユーザーの好みを否定せず、組み合わせの効果を説明する |
| 不確かなとき | 明示する。例：着用イメージで再現しきれていない部分がある場合 |

### 8.2 対話の例

> **ユーザー**：明日は代官山に行くんだけど、グレーのパーカーを使いたい。黒のパンツはもうやめたい。
>
> **StyleAI**：了解です。まずクローゼットで合いそうなものを見てみますね。……インディゴのストレートデニムと白の長袖 T シャツがありました。パーカーのネイビーの胸ロゴが、デニムのブルーと響きます。
>
> 2 案用意しました。
>
> **案 1 · 安定**：白 T をインナーに、グレーのパーカーを普通に着て、インディゴのデニムを一折りして足首を見せ、白のスニーカー。全体が「ニュートラル + 青ひとつ」で、清潔感があって外しません。
>
> **案 2 · 遊ぶ**：パーカーを腰に巻いて、上は白 T のみ。その上にカーキのワークジャケット。腰のグレーが上下を分けて脚のラインが出ますし、ストリート感も出ます。明日の日中は 22 度くらいなので、暑ければジャケットを脱ぎ、寒ければパーカーを着られます。
>
> 着用イメージを生成しています。案 2 は多段階生成なので 1〜2 分かかります。

（トーンと情報の並べ方を示す例であり、実際の出力そのものではありません。天気の情報には天気データの連携が必要で、今後の要件とします。）

## 9. 内蔵モデルライブラリ

- 商用利用可能な画像生成モデルで「実在しない人物」を生成します。モデルごとに参照画像のセット（正面、横、7 分身、ベーシックな白 T と明るいパンツ）を持ち、毎回の生成で本人性の参照に使います。
- 公開前に実在の人物や著名人との類似度をチェックし、モデルカードに生成モデル、日付、ライセンス条件、チェック結果を記録します。
- 第一弾は 4 名（M0）、M3 までに 12 名へ拡張。男女を揃え、複数のスタイル原型と多様なルーツをカバーします。
- Agent が提案のスタイルに合わせて選び、ユーザーが指定することもできます。

## 10. 非機能要件

| 分類 | 要件 |
| --- | --- |
| 応答速度 | メッセージ送信から最初のテキスト出力まで P50 3 秒以内。クローゼット一覧の表示 P95 1 秒以内 |
| 可用性 | クローズドテスト期間中は正式な SLA を設けない。外部サービス障害時は明確に伝え、保存済みデータは失わない |
| プライバシー | アップロード画像は既定で非公開。服・提案・メモリ・アカウントを削除できる。画像が第三者のモデルサービスで処理されることをプライバシーポリシーに明記 |
| 国際化 | 画面、対話、タグ名称が中日英に対応。価格は日本円表示 |
| アクセシビリティ | 主要フローをキーボードで操作できる。コントラストは WCAG AA。画像に代替テキスト |
| 対応環境 | デスクトップとスマホのブラウザ（Chrome、Safari、Edge の最新 2 メジャーバージョン） |
| コスト | 対話 1 ターン、提案 1 件にトークンと生成回数の上限。提案あたりのコスト目標は M0 の実測後に決定 |

| M5 自己学習 | W11–13 | 雑誌学習パイプライン（P0 ソース）、候補カードの評価と審査画面 | 新カード追加後も評価スコアが下がらない |
| M6 仕上げとクローズドテスト | W13–15 | コストとレイテンシの最適化、30 名のクローズドテスト（日本のユーザー） | 保存率・再訪率がベースラインに到達 |

## 12. リスクとコンプライアンス

| リスク | レベル | 対策 |
|---|---|---|
| 雑誌コンテンツの著作権 | 高 | 抽象的なテクニックのみ抽出して書き直し、出典を記録。本文と画像は保存しない。写しチェック。購読サービスの規約を確認 |
| ブランド公式サイトの取得と商品画像の利用 | 高 | アフィリエイト経路を優先。robots と規約を順守。メタデータとリンクのみ保存。着用イメージには「イメージ」と明記 |
| 大手ブランドサイトのボット対策によるデータ不安定 | 高 | M0 からアフィリエイト経路を調査。合法的に取得できないブランドは第一弾から入れ替える |
| モデルの肖像と生成画像の権利 | 高 | 商用利用可能なモデル、類似度チェック、生成元とライセンスの記録 |
| ユーザー画像を第三者サービスに送信すること | 高 | M0 で各サービスのデータ利用条件を確認。プライバシーポリシーで明示 |
| 外部ウェブからのプロンプトインジェクション | 中 | ウェブ内容は構造化フィールドのみ抽出し、システムプロンプトに入れない。ツール権限は現在のユーザーに限定 |
| 服の再現崩れ | 中 | セグメンテーションで元のピクセルを保持。多段階編集 + 真値画像との比較 |
| 変わった着こなしの生成失敗 | 中 | 独立した段階に分け、生成ノウハウを蓄積 |
| ナレッジの劣化や陳腐化 | 中 | 候補 → 評価 → 人の審査。トレンド系は有効期限付き |
| ブランド商品のハルシネーション | 中 | サービス層で検証：カタログ内の在庫品のみ引用可 |
| 提案ごとのコスト超過 | 中 | シンプルな提案は一段階、バックグラウンドは小型モデル、プロンプトキャッシュ、コスト上限 |

## 13. 成功指標（初期値、M0 後に調整）

| 指標 | 定義 | 目標 | 測定方法 |
|---|---|---|---|
| タグ精度 | カテゴリ・メインカラー・素材・シルエットがラベルと一致する割合 | 90% 以上 | 200 着のセット、マイルストーンごとに再測定 |
| 服の再現度 | 人の評価で 4 / 5 以上の画像の割合 | 80% 以上 | 毎週 50 枚を抽出し、2 名が独立に評価 |
| 提案の専門性 | スタイリストのブラインド評価 1–5 | 4.0 以上 | マイルストーンごとに 30 件 |
| 意外な着こなしの採用 | 保存された提案のうち変わった着こなしを含む割合 | 15% 以上 | プロダクトのデータ |
| ブランドリンク有効率 | 提案時点でリンクが開けて在庫あり | 98% 以上 | 巡回の記録 |
| 最初の画像までの時間 | 一段階 P50 / 多段階 P50 | 40s / 120s 以内 | 生成ジョブの記録 |
| 提案の保存率 | 生成された提案のうち保存された割合 | M6 でベースライン確立 | プロダクトのデータ |
| 7 日以内の再訪率 | 初回利用から 7 日以内に再び対話したユーザーの割合 | M6 でベースライン確立 | プロダクトのデータ |
| 提案あたりのコスト | LLM + 画像生成 | M0 実測後に決定 | トレースのコスト記録 |

## 14. 決定が必要な事項

1. **プロダクト名**：StyleAI v2 は仮称。リポジトリ名は `stylist-agent`。
2. **モデルのラインナップ**：第 9 節の第一弾 4 名の方向性で問題ないか、およびルーツの構成。
3. **ビジネスモデル**：クレジット制、ブランドのアフィリエイト、サブスクリプションのいずれか。ブランドとの協業方法とクレジット設計に影響します。
4. **オープンソースライセンス**：現在は公開だがライセンス未付与（All rights reserved）。ビジネスモデル確定後に決めます。
